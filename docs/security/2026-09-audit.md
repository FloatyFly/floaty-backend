# Floaty backend — security audit, September 2026

**Scope:** the `floaty-backend` repository at commit `0b06e6e` (branch `docs/context-security-vocabulary`).
**Status:** Floaty is not yet deployed publicly. Nothing here is a live vulnerability. The findings are
written plainly, as they would read the day the service goes public.
**Deliverable:** this report only. No production code was changed; `src/main/` was read-only for this
audit. The one new file outside `docs/` is `src/test/java/ch/floaty/SecurityAuditTest.java`.

Vocabulary follows `CONTEXT.md`: **Pilot**, **Flight**, **Glider**, **Spot**, **Session**, **Ownership**,
**Finding**. The distinction that matters most below is between *authentication* (is a valid Session
required?) and *Ownership* (may this particular Pilot touch this particular record?).

---

## Executive summary

Three things, in order.

**Ownership is missing on exactly one entity.** `GliderController` and `SpotController` check
ownership on every by-id operation. `FlightController` checks it on create and nowhere else. The
Flight — the record Floaty exists to store — is the one record any logged-in pilot can read, overwrite
and delete for any other pilot. All four Flight findings are pure Ownership failures on endpoints that
*do* correctly require authentication; none is an authentication bypass.

**A database administrator password is published.** `terraform/main.tf` has carried the Azure SQL
admin credentials in cleartext since the initial commit, on a public repository with secret scanning
disabled. Rotating it is the one action that should not wait for this report to be discussed.

**Production runs a development profile.** The Helm Deployment sets `SPRING_PROFILES_ACTIVE:
dev-mysql`, so `application-prod.properties` describes a configuration that never loads. What actually
runs has Hibernate auto-migrating the live schema, a `localhost` origin in the credential-trusted CORS
allowlist, and mail pointed at an SMTP server absent from the pod — meaning **registration and
password reset do not work at all** in the deployed configuration. Any reader of an earlier draft of
this report should note that its mail and seed-data findings cited the wrong file.

## Findings

### Scope area 3 — Endpoint authorization (Ownership)

These four findings share one root cause and one fix. `FlightController` resolves a Flight by the id
in the path and never compares `flight.getUser()` to the authenticated Pilot.
`FlightApplicationService` calls unscoped `CrudRepository` primitives (`findById`, `deleteById`); the
one user-scoped repository method, `IFlightRepository.findByUser`, is used only by the collection
endpoint `GET /flights`, which is correctly scoped.

For contrast, `GliderController.java:93`, `:114`, `:155` and `SpotController.java:91`, `:112`, `:151`
all perform exactly the check that is missing here. The pattern to copy already exists in the
codebase.

**What an attacker needs to start:** one ordinary Floaty account — register, verify the email, log in.
Flight ids are sequential (`GenerationType.AUTO`), so enumeration is trivial. No stolen cookie, no
ADMIN, no network position.

---

#### FLOATY-SEC-001 — Any pilot can delete any pilot's flight

**Severity: Critical.** Any logged-in pilot can permanently delete another pilot's flight. Iterating
over sequential ids destroys an entire logbook, and there is no soft-delete or audit trail — the row
is gone.

- **Location:** `src/main/java/ch/floaty/infrastructure/FlightController.java:141-150`
- **Why it is exploitable:** the method carries **no** `@PreAuthorize` and no ownership check of any
  kind. It is still authentication-gated, by `anyRequest().authenticated()` at
  `src/main/java/ch/floaty/config/SecurityConfig.java:45` — so this is an Ownership failure, not an
  authentication bypass. The call path is
  `deleteFlight(flightId)` → `FlightApplicationService.java:69-71` → `flightRepository.deleteById(flightId)`,
  a plain unscoped `CrudRepository` delete. `DELETE /flights/42` from any account removes flight 42.
- **Challenged:** survived. The challenger could construct no reading — filter, matcher,
  `@PreAuthorize`, service check or database constraint — in which ownership is enforced on this path,
  and confirmed the repository call is an unscoped primitive.
- **Fix direction:** load the Flight, compare its `user` to the authenticated Pilot, and return 403
  (or 404, to avoid confirming the id exists) before deleting — the check already written three times
  in `GliderController`.

#### FLOATY-SEC-002 — Any pilot can overwrite any pilot's flight

**Severity: High.** Any logged-in pilot can rewrite the date, duration and description of another
pilot's flight. The logbook silently becomes wrong, which for a pilot logging hours toward a licence
or currency requirement is a records-integrity problem, not just a nuisance.

- **Location:** `src/main/java/ch/floaty/infrastructure/FlightController.java:97-118`
- **Why it is exploitable:** `@PreAuthorize("isAuthenticated()")` at `:98` requires a Session and
  nothing more. `:100` loads the Flight by id and never checks its owner. Secondarily, the referenced
  `launchSpotId` / `landingSpotId` / `gliderId` are resolved at `:109-111` with no ownership check
  either — so the attacker can re-point a victim's flight at the attacker's own Spots and Glider.
  Note the contrast with `createFlight`, which *does* check exactly this at `:58` and `:67`.
- **Challenged:** survived. The challenger confirmed the missing check and noted that overwriting the
  victim's flight is the more severe half of the finding; severity unaffected.
- **Fix direction:** same ownership check as SEC-001, plus reuse the create path's spot/glider
  ownership validation so update and create agree.

#### FLOATY-SEC-003 — Any pilot can read any pilot's flight record

**Severity: Medium.** Any logged-in pilot can read another pilot's flight: date, duration, free-text
description, and the ids of the spots and glider used.

- **Location:** `src/main/java/ch/floaty/infrastructure/FlightController.java:129-139`
- **Why it is exploitable:** `@PreAuthorize("isAuthenticated()")` only; `findFlightById`
  (`FlightApplicationService.java:74-76`) is a bare `findById` with no owner filter.
- **Challenged:** survived at Medium. The challenger agreed Medium is right for a read-only
  disclosure of non-track data, keeping the track disclosure separate as SEC-004.
- **Fix direction:** as SEC-001.

#### FLOATY-SEC-004 — Any pilot can download any pilot's GPS track

**Severity: High.** Any logged-in pilot can download another pilot's raw IGC file and parsed GPS
track. IGC B-records carry timestamped latitude, longitude and altitude for the whole flight, so this
discloses precise launch and landing coordinates and the full route. Pilots frequently launch and land
near home; a repeated landing coordinate across a pilot's flights is effectively a home address, and
the timestamps say when they were away from it.

- **Location:** `src/main/java/ch/floaty/infrastructure/FlightController.java:152-162` (`/igc`) and
  `:164-175` (`/track`)
- **Why it is exploitable:** both are `@PreAuthorize("isAuthenticated()")` with no ownership check.
  `/igc` returns the stored `IgcData.file` (`IgcData.java:24-26`, a `@Lob byte[]`) verbatim; `/track`
  returns it parsed into `TrackPoint`s. The B-record format is visible in the seed data at
  `src/main/resources/data.sql:273-288`.
- **Challenged:** survived at High. The challenger agreed the location sensitivity of track data
  warrants a step above SEC-003's Medium.
- **Fix direction:** as SEC-001, applied to both endpoints.

### Scope area 1 — Authentication

#### FLOATY-SEC-016 — Password-reset mail can be triggered cross-site and unthrottled

**Severity: Medium.** Any web page in any browser can make Floaty send password-reset mail to any
address it chooses, as fast as it likes. Two consequences: a victim pilot can be buried in reset mail
they did not ask for, and Floaty's SendGrid reputation absorbs the resulting spam complaints.

- **Location:** `src/main/java/ch/floaty/infrastructure/AuthenticationController.java:72-77`
- **Why it is exploitable:** the parameter is `@RequestBody String email` with no `consumes`
  restriction, so Spring binds it with `StringHttpMessageConverter`, which accepts **`text/plain`**.
  `text/plain` is a CORS-*simple* content type: a plain cross-site HTML form can POST it with **no
  preflight**, so neither the CORS allowlist (`SecurityConfig.java:59-70`) nor the disabled CSRF
  protection stops it. Every other state-changing endpoint takes a JSON DTO and is therefore
  preflight-gated — this one is the exception. There is also no rate limit on
  `initiatePasswordReset` (`AuthenticationService.java:132-146`), which sends a mail per call.
  **Verified empirically:** a `POST` with `Content-Type: text/plain` to
  `/auth/initiate-password-reset` returns **200**.
- **What an attacker needs to start:** a web page. No Floaty account, no session, no network position.
- **Challenged:** **added during Pass 1.** The challenger's argument for downgrading SEC-008 was that
  JSON content types force a preflight; that reasoning is correct but has this one verified exception,
  which the challenger's pass had not covered. Found by testing the claim rather than accepting it.
- **Fix direction:** constrain the endpoint to `consumes = "application/json"` with a proper DTO, and
  rate-limit reset initiation per address and per source IP.

#### FLOATY-SEC-020 — Registration discloses which email addresses have accounts

**Severity: Low.** Anyone can determine whether a given email address or username belongs to a Floaty
pilot, without an account. For a flight log tied to real names and home coordinates, membership is
itself information a pilot may not want public.

- **Location:** `src/main/java/ch/floaty/domain/service/AuthenticationService.java:55-58`, surfaced by
  `src/main/java/ch/floaty/infrastructure/ControllerExceptionHandler.java:38-41` and `:58-61`
- **Why it is exploitable:** `register` throws `UserAlreadyExistsException` ("The provided username is
  already taken.") or `EMailAlreadyUsedException` ("A user with this email address already exists.")
  and the handler returns each message verbatim with a 400. Submitting a registration for a candidate
  address distinguishes "registered" from "not registered" by response body.
- **Worth crediting:** the **login** path does *not* have this problem. `login` throws distinct
  `UserNotFoundException` and `WrongPasswordException` internally
  (`AuthenticationService.java:94-104`), but `AuthenticationController.java:53-56` catches both and
  returns a uniform 401 with no body. That is the correct pattern, and it is already in the codebase —
  registration simply does not follow it. Password reset is likewise careful: the response is
  deliberately neutral ("if it exists") at `AuthenticationController.java:75`.
- **Challenged:** added during Pass 2 review of scope area 1; the uniform-401 login behaviour was
  verified rather than assumed, so the finding is scoped to registration only.
- **Fix direction:** return a generic failure from registration, or move to an
  email-confirmation-first flow where existence is never revealed synchronously.

#### FLOATY-SEC-023 — No rate limiting on login or registration

**Severity: Medium.** Nothing limits how fast an attacker can guess passwords. There is no rate limit,
no account lockout, no backoff and no CAPTCHA on `POST /auth/login`, and none on `/auth/register`
either.

- **Location:** `src/main/java/ch/floaty/infrastructure/AuthenticationController.java:48-64`;
  no limiting exists anywhere in `src/main/java/` (no filter, no interceptor, no bucket).
- **Why it is exploitable:** bcrypt at work factor 10 makes each attempt cost the *server* real CPU,
  which bounds throughput somewhat, but nothing bounds *attempts per account*. Credential stuffing
  against known-breached password lists proceeds unimpeded, and failed logins are logged at INFO
  (`:54`) without any counter or alert attached.
- **Why this one matters more than usual here:** it is the missing brake in the
  [SEC-011](#floaty-sec-011--a-seeded-account-is-re-inserted-on-every-boot) chain. The seeded
  `Floater` account's bcrypt hash is committed to a public repository, so it can be attacked offline
  with no interaction; once a candidate password is found, there is nothing on the live endpoint to
  slow using it, and the account is already `email_verified=TRUE`.
- **Challenged:** added during Pass 2. The draft had flagged missing rate limiting only for password
  reset (SEC-016) and had not generalised it to the credential endpoints.
- **Fix direction:** per-account and per-IP attempt limiting with exponential backoff, plus temporary
  lockout after a threshold.

#### FLOATY-SEC-024 — Nonexistent flight ids return 500, disclosing which ids exist

**Severity: Low.** Any logged-in pilot can determine exactly which flight ids exist in the database,
cheaply and reliably, by watching the status code.

- **Location:** `src/main/java/ch/floaty/domain/service/FlightApplicationService.java:74-76`, surfaced
  by `src/main/java/ch/floaty/infrastructure/ControllerExceptionHandler.java:22-26`
- **Why it is exploitable:** `findFlightById` is
  `findById(...).orElseThrow(() -> new IllegalArgumentException("Flight not found"))` — it **never
  returns null**. The null checks at `FlightController.java:133`, `:156` and `:168` are therefore dead
  code and the intended 404 never fires. `IllegalArgumentException` has no handler, so it falls to the
  generic handler and returns **500**. An existing id returns 200; a nonexistent one returns 500.
  **Verified empirically:** a request for a nonexistent id returns 500, not 404.
- **Two consequences:** it hands an attacker a free id-enumeration primitive that makes
  [SEC-004](#floaty-sec-004--any-pilot-can-download-any-pilots-gps-track) exhaustive rather than
  targeted (see [Chain 4](#chained-attacks)); and every probe writes a full stack trace at ERROR
  (`ControllerExceptionHandler.java:24`), so an enumeration sweep is also a log-flooding vector.
- **Challenged:** added during Pass 2, which caught that the report's own fix direction for SEC-001
  ("return 404 to avoid confirming the id exists") was written as though 404 were the current
  behaviour. It is not — the oracle already exists.
- **Fix direction:** map `IllegalArgumentException` to 404 in the handler, or have the service return
  `Optional` and let the controllers decide; then delete the dead null checks.

#### FLOATY-SEC-025 — Session tokens accumulate forever and are looked up without an index

**Severity: Low.** Expired session tokens are never deleted from `t_session_token`, and the column
they are looked up by has no index, so every authenticated request runs a full table scan over a table
that only grows.

- **Location:** `src/main/resources/schema-mysql.sql:96-105`; lookup at
  `ISessionTokenRepository.findByToken`, called on every request from `SessionTokenFilter.java:50`
- **Why it matters:** there is no scheduled cleanup anywhere in `src/main/java/` — no `@Scheduled`, no
  purge, no TTL job. Rows are removed only by logout and password reset
  (`AuthenticationService.java:164`, `:174`), so every session a pilot abandons without logging out
  leaves a permanent row. `token` carries neither a `UNIQUE` constraint nor an index, so `findByToken`
  degrades linearly. This is availability drift rather than an attack, but a login endpoint with no
  rate limit ([SEC-023](#floaty-sec-023--no-rate-limiting-on-login-or-registration)) lets an attacker
  create rows on demand and accelerate it.
- **Challenged:** added during Pass 2; the absence of any cleanup and of an index were both verified
  against the schema and a search of the source.
- **Fix direction:** add a unique index on `token`, and reap expired rows on a schedule.

#### FLOATY-SEC-021 — Email verification tokens are never consumed

**Severity: Low.** A verification link keeps working for its full 30-minute lifetime after it has been
used, instead of being spent on first use.

- **Location:** `src/main/java/ch/floaty/domain/service/AuthenticationService.java:113-130`
- **Why it matters:** `verifyEmail` sets `emailVerified` on the User but never deletes the token nor
  marks it used — `EmailVerificationToken` has no `used` flag at all, unlike `PasswordResetToken`
  which has one (`PasswordResetToken.java:19`) and checks it (`AuthenticationService.java:157-160`).
  Replay is currently harmless because the second attempt is rejected by the
  `user.isEmailVerified()` guard at `:123`, so this is defence-in-depth rather than a live hole. It
  becomes exploitable the moment verification is reused for anything else — an email-change flow being
  the obvious candidate — because the token would then still be live in whatever inbox or proxy log it
  passed through.
- **Challenged:** added during Pass 2; survived with severity held at Low precisely because the
  `isEmailVerified` guard blocks the replay today. Recorded so the guard is not silently removed later.
- **Fix direction:** delete the token on successful verification, mirroring the single-use handling
  `PasswordResetToken` already implements.

### Scope area 2 — Session management

#### FLOATY-SEC-009 — Sessions have no absolute lifetime

**Severity: Medium.** A stolen session cookie stays valid forever, as long as it is used at least once
every ten minutes. A pilot who logs out on a shared machine is fine; a pilot whose cookie leaked has
no way to age the attacker out.

- **Location:** `src/main/java/ch/floaty/domain/service/SessionTokenService.java:26-29`
- **Why it is exploitable:** `renewToken` unconditionally sets expiry to `now + 10 minutes` on every
  authenticated request (called from `SessionTokenFilter.java:58`). `TimedToken` stores only
  `expirationTime` — there is no `createdAt` and so no ceiling. The sliding expiry is intentional and
  documented in `CONTEXT.md`; the absent *cap* is the gap.
- **What an attacker needs to start:** an already-stolen token. This is a severity-limiting
  precondition, hence Medium rather than High.
- **Challenged:** survived at Medium; the challenger confirmed there is no absolute cap and agreed the
  stolen-token precondition holds it at Medium.
- **Fix direction:** record `createdAt` on `SessionToken` and refuse renewal past a fixed absolute age
  (a working day is typical), forcing re-authentication.

#### FLOATY-SEC-014 — `revoked` is dead code (no missing control)

**Severity: Informational.** `TimedToken.java:21` declares a `revoked` flag, sets it `false` in the
constructor (`:27`), and no code ever reads or writes it again; the column exists in
`schema-mysql.sql:102`. Revocation *is* implemented, by deleting rows — logout at
`AuthenticationService.java:174` and password reset at `:164` both delete every token for the pilot.
So there is no missing control here, only a misleading field.

- **Challenged:** survived as characterised — the challenger confirmed revocation works via deletion
  and agreed this is cleanup, not a security finding.
- **Fix direction:** delete the field and column, or start using it instead of row deletion.

### Scope area 4 — Spring Security configuration

#### FLOATY-SEC-008 — CSRF is disabled

**Severity: Low** (downgraded from Medium). `SecurityConfig.java:47` disables CSRF while sessions ride
on a cookie with no `SameSite` (SEC-006) — the textbook precondition for cross-site state change.

What holds it at Low: every state-changing endpoint except one binds a JSON `@RequestBody` DTO. A
cross-site HTML form can only send `application/x-www-form-urlencoded`, `multipart/form-data` or
`text/plain`, none of which bind to those DTOs; and a `fetch` with `Content-Type: application/json`
triggers a CORS preflight, which the fixed origin allowlist (`SecurityConfig.java:59-70`) does gate.

- **Challenged:** downgraded from Medium to Low, reason recorded: CORS does not stop CSRF in general
  — the browser sends the request and only withholds the response — but the JSON content-type
  requirement plus preflight blunts classic form-based CSRF here. The residual risk is a future
  form-encoded endpoint or a loosened origin allowlist. **The one endpoint that escapes this
  reasoning is now tracked separately as [SEC-016](#floaty-sec-016--password-reset-mail-can-be-triggered-cross-site-and-unthrottled).**
- **Fix direction:** re-enable CSRF with a cookie/header token pair, or set `SameSite=Lax` (SEC-006),
  which closes the cross-site path independently.

#### FLOATY-SEC-007 — `/auth` prefix bypass is not exploitable

**Severity: Informational** (downgraded from Low). `SessionTokenFilter.java:43` tests
`request.getRequestURI().startsWith("/auth")`, a prefix match rather than a path-segment match, so a
URI like `/authsomething` also skips token validation.

This grants nothing. The filter only *populates* the `SecurityContext`; authorization is enforced by
the matchers at `SecurityConfig.java:41-46`. `/authsomething` does **not** match the ant pattern
`/auth/**` (which requires the segment boundary), so it falls through to `anyRequest().authenticated()`
— and with the filter skipped, no `Authentication` was set, so the request is rejected. No endpoint is
mapped there in any case.

**Two details of the actual control flow**, both of which the first write-up of this finding got
wrong and Pass 2 corrected:

- The `/auth` test at `:43` sits **after** an early return for a missing cookie (`:37-40`), so it is
  reached only when a `sessionToken` cookie is present. A request with no cookie never gets that far.
- The carve-out is already an **exact** `equals("/auth/logout")`, not a prefix — so the fix direction
  originally proposed here ("compare against `/auth/` with an exact-match carve-out for
  `/auth/logout`") described what the code does today. What remains genuinely loose is only the
  `startsWith("/auth")` half.
- The exact-match carve-out and the chain's `antMatchers("/auth/logout")` (`SecurityConfig.java:43`)
  can diverge on variant spellings: `/auth/logout/` or `/auth/logout;jsessionid=x` fail the filter's
  `.equals()`, so the token is never validated and no `Authentication` is set. The request is then
  rejected by `authenticated()` — safe, but safe by accident rather than by the reasoning originally
  given.

- **Challenged:** downgraded from Low to informational in Pass 1, which traced the matcher semantics
  and showed the skipped filter causes rejection rather than bypass. Pass 2 then corrected the
  mechanism described above and struck the proposed fix as already-implemented. Recorded anyway
  because the next `/auth`-prefixed route added to the app is where the loose prefix becomes a real
  bug.
- **Fix direction:** tighten the prefix test to `"/auth/"` (the logout carve-out already being exact),
  and normalise the URI before matching so path variants cannot diverge from the chain's matchers.

### Scope area 5 — Management / actuator surface

#### FLOATY-SEC-005 — Actuator on port 8081 is unauthenticated

**Severity: Low** (downgraded from Medium). The `@Order(1)` chain at
`src/main/java/ch/floaty/config/ManagementSecurityConfig.java:15-31` matches any request whose
`getLocalPort()` is 8081 and applies `anyRequest().permitAll()`. `application.properties:11-14` puts
`health`, `prometheus` and `metrics` on that port, and `helm/floaty-chart/templates/service.yaml:12-14`
exposes 8081 on the Service.

Two mitigations, both verified: the **Ingress routes only port 80**
(`helm/floaty-chart/templates/ingress.yaml`), so 8081 is never publicly reachable and an attacker must
already be inside the cluster; and `management.endpoint.health.show-details=when-authorized`
(`application.properties:13`) withholds component details from unauthenticated callers. What actually
leaks is JVM and HTTP operational telemetry — which is exactly what the ServiceMonitor is meant to
scrape.

**Both deployment topologies were checked**, not just Helm. `docker-compose.yml:6-7` publishes only
`8080:8080`, leaving 8081 unmapped and unreachable from the host. The legacy Azure path in
`terraform/main.tf:203-216` sets `WEBSITES_PORT = "8080"`, so Azure App Service routes only 8080, and
`https_only = true` at `:207` forces TLS there. In no configured topology is 8081 publicly exposed.

- **Challenged:** downgraded from Medium to Low, reason recorded: the challenger checked the Ingress
  and the `show-details` setting, and established that exposure requires in-cluster network position
  and yields telemetry, not pilot data. Pass 2 additionally confirmed the compose and Azure paths.
- **Fix direction:** restrict 8081 with a NetworkPolicy admitting only the Prometheus scraper, and
  keep the port off the public Ingress as it already is.

### Scope area 6 — Transport and cookie security

#### FLOATY-SEC-006 — Session cookie has no `Secure` and no `SameSite`

**Severity: Medium.** Without `Secure`, a browser will send the session cookie over plaintext HTTP, so
any downgrade or plain-HTTP request on the domain exposes it. Without `SameSite`, the cookie rides
cross-site requests, which is the precondition SEC-008 depends on.

- **Location:** `src/main/java/ch/floaty/infrastructure/AuthenticationController.java:57-60` (and the
  matching logout cookie at `:93-97`)
- **Why it is exploitable:** the cookie is built with the servlet `Cookie` API and sets only
  `HttpOnly` and `Path`. `HttpOnly` is correct and does block script access; `Secure` and `SameSite`
  are simply absent, and the servlet `Cookie` API in this Spring version has no `SameSite` setter — it
  needs a `Set-Cookie` header or `server.servlet.session.cookie.same-site`.
- **Challenged:** survived at Medium; citation and absence of both attributes verified.
- **Fix direction:** set `Secure` (conditioned on profile so local HTTP dev still works) and
  `SameSite=Lax`.

#### FLOATY-SEC-017 — Mail is sent to `localhost` in the deployed configuration, and without TLS wherever it is sent

**Severity: High.** Every account-lifecycle mail — email verification and password reset — is
addressed to an SMTP server that does not exist in the deployed pod. Registration cannot be completed
and no pilot can recover a password. Wherever mail *is* eventually sent, it goes without TLS.

- **Location:** `src/main/resources/application-dev-mysql.properties:25-33` (the deployed profile) and
  `src/main/resources/application-prod.properties:19-28` (the profile that is never activated)
- **Why it is broken:** the Helm Deployment sets `SPRING_PROFILES_ACTIVE: dev-mysql`
  (`helm/floaty-chart/templates/deployment.yaml:33-34`) — **not `prod`**. That profile points mail at
  `spring.mail.host=localhost`, `spring.mail.port=2525`, which is the local smtp4dev container from
  `docker-compose.yml:67-76`. The Deployment defines a **single container** with no smtp4dev sidecar,
  and no SMTP service exists anywhere in `helm/` or `argocd/`, so nothing listens on `localhost:2525`
  in that pod. `mailSender.send` therefore throws, and since `register` and `initiatePasswordReset`
  are `@Transactional` (`AuthenticationService.java:23`), the resulting `MailSendException` rolls the
  transaction back — so **registration does not merely fail to send mail, it fails outright**, and the
  caller receives a 500 from `ControllerExceptionHandler.java:22-26`.
- **The TLS half, which applies to whichever profile is used:** both the deployed `dev-mysql` profile
  (`:30-31`) and the unused `prod` profile (`:26-27`) set `mail.smtp.auth=false` and
  `mail.smtp.starttls.enable=false`. In `prod` those settings sit alongside
  `spring.mail.host=smtp.sendgrid.net` on port 587 and `spring.mail.password=${SENDGRID_API_KEY}` —
  an API key that `auth=false` means is never presented. Whoever fixes the profile inherits reset
  tokens crossing the network in cleartext unless the TLS settings are fixed at the same time.
- **Two further consequences of the same profile mix-up**, both live: `app.base.url` and
  `email.verification.url` point at `http://localhost:8200` (`:2`, `:33`), so any link Floaty did
  manage to send would be unusable; and `cors.allowedOrigins` includes `http://localhost:8200` (`:5`)
  in the deployed configuration — see [SEC-022](#floaty-sec-022--the-deployed-profile-is-dev-mysql-not-prod).
- **Challenged:** **substantially rewritten after Pass 2.** The original finding described SendGrid on
  port 587 and was scoped at Medium — it analysed `application-prod.properties`, a file the running
  service never loads. Pass 2 caught that the Helm Deployment activates `dev-mysql`. Verified
  independently: the profile value, the single-container spec, and the absence of any SMTP service in
  the cluster manifests. Severity raised Medium → High, because a broken registration and password-reset
  flow is worse than a TLS gap.
- **Fix direction:** point the deployed profile at the real mail host with `auth=true`,
  `starttls.enable=true` and `starttls.required=true` — and, more fundamentally, stop deploying a
  `dev-*` profile to production (SEC-022).

### Scope area 7 — Input validation and injection surface

#### FLOATY-SEC-010 — Request validation is a no-op and IGC uploads are unbounded

**Severity: Medium.** A pilot can upload an arbitrarily large "IGC file" and Floaty will store the
whole thing in the database. Repeated, this exhausts storage for everyone.

- **Location:** `src/main/java/ch/floaty/infrastructure/FlightController.java:48`,
  `GliderController.java:42`, `SpotController.java:39`, `:102`; storage at
  `src/main/java/ch/floaty/domain/model/IgcData.java:24-26`
- **Why it is exploitable:** the controllers annotate request bodies `@Validated`, but the
  OpenAPI-generated DTOs carry **no Bean Validation annotations at all** — `api/floaty-open-api.yml`
  declares only `required:` (schema presence), never `maxLength`, `pattern`, `minimum` or `maximum`,
  so the generator emits plain POJOs and `@Validated` has nothing to enforce. Nothing bounds
  `description` fields, and nothing bounds the base64 `file` in `FlightCreateIgcDataCreateDto`, which
  is persisted as a `@Lob byte[]` and parsed by `FlightTrack`. There is no request size limit
  configured anywhere in `src/main/resources/`.
- **On the specific IGC parser risks in scope:** the parser (`FlightTrack.java:165-358`) is a
  hand-written line scanner, not an XML or zip reader — so there is **no** entity expansion or zip-bomb
  surface, and malformed records are skipped rather than throwing (`:246-249`). The real exposures are
  the unbounded allocation above and a recursive Douglas-Peucker implementation
  (`TrackSimplifier.java:40-71`) that recurses per segment and could stack-overflow on a crafted
  track; that would be caught by the handler at `ControllerExceptionHandler.java:22-26` as a 500.
- **Challenged:** survived at Medium, with one correction adopted: `spring.servlet.multipart.max-file-size`
  would *not* help, because the IGC arrives base64-encoded inside a JSON body rather than as multipart.
  The report text above was corrected accordingly.
- **Fix direction:** add `maxLength` to the OpenAPI schemas so the generator emits real constraints,
  and enforce an explicit byte ceiling on IGC uploads before persisting.

**No injection surface found.** All persistence goes through Spring Data derived query methods and
`CrudRepository`; there is no string-concatenated SQL or JPQL anywhere in `src/main/`, and no
user-controlled input reaches the filesystem.

### Scope area 8 — Secrets and configuration

#### FLOATY-SEC-022 — The deployed profile is `dev-mysql`, not `prod`

**Severity: High.** Production runs on a development profile. This is not a finding in its own right so
much as the root cause of several others, and it is the reason a reader must not take
`application-prod.properties` as a description of the running service.

- **Location:** `helm/floaty-chart/templates/deployment.yaml:33-34`

```yaml
- name: SPRING_PROFILES_ACTIVE
  value: dev-mysql
```

- **What is actually live**, from `src/main/resources/application-dev-mysql.properties`:

| Setting | Deployed (`dev-mysql`) | Unused (`prod`) | Consequence |
|---|---|---|---|
| `spring.jpa.hibernate.ddl-auto` | `update` (`:20`) | `validate` | Hibernate silently alters the live schema to match entity changes — an unreviewed field rename becomes a production migration with no gate. |
| `spring.mail.host` / `port` | `localhost:2525` (`:26-27`) | `smtp.sendgrid.net:587` | No SMTP in the pod: registration and password reset are broken ([SEC-017](#floaty-sec-017--mail-is-sent-to-localhost-in-the-deployed-configuration-and-without-tls-wherever-it-is-sent)). |
| `cors.allowedOrigins` | includes `http://localhost:8200` (`:5`) | same, also includes it | A localhost origin is credential-trusted in production — see below. |
| `app.base.url` / `email.verification.url` | `http://localhost:8200` (`:2`, `:33`) | `https://app.floatyfly.com` | Any emitted link is unusable. |
| `spring.sql.init.mode` | `always` (`:14`) | `always` | Seed data re-inserted every boot ([SEC-011](#floaty-sec-011--a-seeded-account-is-re-inserted-on-every-boot)). |

- **The CORS consequence is the security-relevant one.** `SecurityConfig.java:59-70` builds the CORS
  policy from `cors.allowedOrigins` with `setAllowCredentials(true)`. Because
  `http://localhost:8200` is on that list in the deployed configuration, any page a victim can be
  induced to load on their own machine's port 8200 is a fully credential-trusted origin against
  production. This weakens the reasoning behind the [SEC-008](#floaty-sec-008--csrf-is-disabled)
  downgrade, which leaned on the origin allowlist being a meaningful gate — it is a meaningful gate
  only for origins an attacker cannot occupy, and `localhost` is not one of those.
- **Deployment is automatic and ungated.** `argocd/apps/floaty-backend.yaml` syncs `helm/floaty-chart`
  from `main` with `automated: {prune: true, selfHeal: true}`, so whatever lands on `main` reaches
  production with no manual approval step.
- **Challenged:** **added during Pass 2**, which found it by reading the Helm chart rather than the
  properties files. Verified independently: the profile value, `ddl-auto=update`, the localhost CORS
  origin, and the ArgoCD auto-sync policy. Neither the draft nor Pass 1 questioned which profile was
  live — both assumed the file named `prod` described production, which is precisely the assumption
  the ticket warned against by asking for verification over assumption.
- **Fix direction:** introduce a real production profile with `ddl-auto=validate`, no seed data, no
  localhost origins, and correct mail settings; set it in the Deployment. Restrict `dev-*` profiles to
  local use.

#### FLOATY-SEC-011 — A seeded account is re-inserted on every boot

**Severity: Medium** (downgraded from High). `src/main/resources/data.sql:5-6` seeds a fixed,
already-email-verified account — `Floater` / `floater@example.com` — with a committed bcrypt hash.
`spring.sql.init.mode=always` is set in **both** the deployed `dev-mysql` profile
(`application-dev-mysql.properties:14`) and the unused `prod` profile
(`application-prod.properties:12`), so `data.sql` runs on **every** boot regardless of `ddl-auto`.
The `prod` file's own TODO at `:11` warns about exactly this.

- **Why it matters:** the running service gets a predictable, pre-verified account with a fixed
  username and a fixed id of 1, owning 50 spots, 5 gliders and 101 flights. `email_verified=TRUE`
  means it bypasses the verification gate that `login` enforces at `AuthenticationService.java:97`.
  Whether it is a usable back door depends entirely on whether the password behind that hash is weak.
- **Challenged:** downgraded from High to Medium in Pass 1, reason recorded: the original wording
  called it a "known-credential account", but a bcrypt hash is not a disclosed credential, and the
  challenger declined to assert crackability without demonstrating it. Pass 2 then corrected the
  citation — the original cited only the `prod` profile, which is not the one that runs — and drew the
  chain that makes the severity concrete: the hash is in a **public** repository, so it can be attacked
  offline at leisure, and [SEC-023](#floaty-sec-023--no-rate-limiting-on-login-or-registration) means
  nothing on the live endpoint slows the eventual login. It returns to High if the password is shown
  to be weak.
- **Fix direction:** set `spring.sql.init.mode=never` for any deployed profile and keep seed data to
  local development.

#### FLOATY-SEC-019 — Azure SQL administrator password committed in cleartext

**Severity: High.** The administrator login and password for the Azure SQL Server are hardcoded in a
tracked file on a **public** repository, and have been since the initial commit.

- **Location:** `terraform/main.tf:147-148`

```hcl
administrator_login          = "floaty-user"
administrator_login_password = "floaty-password"
```

- **Why it is exploitable:** this is the server-level administrator credential for
  `azurerm_mssql_server.floaty` — full control of the database, not an application-scoped user. The
  repository is public, so the value is readable by anyone, and `git log` shows it entering in
  `268b3c9`, the initial commit — so it is in history as well as at HEAD and cannot be removed by a
  simple follow-up commit. Reachability depends on the Azure firewall rules at `:182-188`, which admit
  only the App Service outbound IPs — but a firewall is the only thing standing between a published
  password and the database, and firewall rules are a configuration away from changing.
  **Secret scanning and push protection are both disabled** on this repository, which is why nothing
  flagged it (see [Platform configuration](#platform-configuration)).
- **What an attacker needs to start:** the ability to read a public GitHub repository, plus a network
  path to the SQL server admitted by the firewall rules.
- **Challenged:** **added during Pass 2**, which found it by examining `terraform/` — a directory the
  ticket named under scope area 5 but that the Pass 1 finding list had only considered for topology,
  never for secrets. Neither the draft nor Pass 1 caught it.
- **Fix direction:** rotate the password immediately — treat it as compromised, since publication is
  not undone by a rotation commit. Move the value to a Terraform variable sourced from a secret store,
  and enable secret scanning with push protection.

#### FLOATY-SEC-018 — Development database password committed

**Severity: Low.** `init.sql:4` commits `CREATE USER 'db-user'@'%' IDENTIFIED BY 'db-password'`, and
the same pair appears in `application-dev-h2.properties:11-12`. These are development credentials for
a local container, and the Helm and compose paths use env vars and SealedSecrets instead — so the
exposure is only that a real deployment which ever reuses this script inherits a known password, and
that `'%'` grants from any host.

- **Challenged:** confirmed in Pass 2 as correctly scoped at Low — genuinely dev-only, unlike
  [SEC-019](#floaty-sec-019--azure-sql-administrator-password-committed-in-cleartext).
- **Fix direction:** parameterise `init.sql` from the environment, as `docker-compose.yml` already does.

**Verified, not assumed — `.env` is genuinely clean.** The ticket asked for verification rather than
assumption. `.gitignore:6` matches `*.env`; `git check-ignore -v .env` confirms the rule applies to
the working-tree file; and `git log --all --diff-filter=A --name-only` over the entire history returns
**no `.env` file ever added** — the only matches are `scripts/config.env.example` (a template) and
SealedSecret manifests. Those manifests (`argocd/sealed-secrets/*.yaml`) contain Bitnami-encrypted
ciphertext, which is designed to be committed and is not readable without the cluster's private key.
Runtime credentials reach the app as environment variables: `MYSQL_PASSWORD` and `SENDGRID_API_KEY` via
`secretKeyRef` in `helm/floaty-chart/templates/deployment.yaml:37-46`, and via required `.env`
variables in `docker-compose.yml:10-13`.

**But "`.env` is clean" is not "no secrets are committed"** — and conflating the two is exactly how
[SEC-019](#floaty-sec-019--azure-sql-administrator-password-committed-in-cleartext) survived the first
pass. The application's runtime secret handling is genuinely sound; the *infrastructure* code is where
a cleartext database administrator password sits, in `terraform/main.tf`. The lesson for the next
audit is that "how do credentials reach the app" and "what is committed" are separate questions, and
answering the first well says nothing about the second.

**What is logged.** No credential is logged. `AuthenticationService` logs usernames and email
addresses at INFO on register, verify, reset and logout (`:44`, `:129`, `:142`, `:168`, `:175`), and
`AuthenticationController.java:54` logs failed-login usernames — personal data at INFO, worth a
retention decision before launch, but not a secrets leak. `server.error.include-stacktrace=never`
(`application.properties:6`) correctly keeps stack traces out of responses.

### Findings recorded as not defects — so they are not re-litigated

#### FLOATY-SEC-015 — ADMIN is unreachable (no defect)

`User.getAuthorities()` (`src/main/java/ch/floaty/domain/model/User.java:36-40`) hardcodes
`List.of(new SimpleGrantedAuthority("ROLE_USER"))`. There is no roles column on `User` and no code path
anywhere grants `ADMIN`. So `GET /users` and `DELETE /users/{id}`
(`UserController.java:30`, `:45`, guarded by `hasAuthority('ADMIN')`) are permanently unreachable —
**fail-closed, which is the safe direction**. Doubly so: even a granted `ROLE_ADMIN` would not satisfy
`hasAuthority('ADMIN')`, which compares the literal string.

A consequence worth stating: `UserSecurity.hasUserIdOrAdmin` (`UserSecurity.java:13-29`) reduces to a
pure Ownership check, since `isAdmin` is always false. `GET /users/{userId}` is therefore correctly
scoped to the requesting pilot today — but it is relying on a coincidence. If ADMIN is ever
implemented, that endpoint silently widens.

- **Challenged:** confirmed as the correct reading; the challenger searched for any ADMIN-granting
  path and found none.

#### FLOATY-SEC-013 — `@OneToOne` on `TimedToken.user` constrains nothing

`TimedToken.java:30-32` maps `user` as `@OneToOne`, which reads as "one token per pilot". It is a JPA
mapping hint only: the DDL at `schema-mysql.sql:96-105` has a plain foreign key with **no UNIQUE
constraint**, so multiple concurrent sessions per pilot work — and the code depends on that, since
login always inserts a fresh `SessionToken` (`AuthenticationService.java:99-100`) and logout deletes a
`List` of them (`ISessionTokenRepository:10`). Misleading, not exploitable.

- **Challenged:** survived as characterised — a modelling correctness note, not a defect.
- **Fix direction:** change to `@ManyToOne`, which is what the schema and the code both mean.

## Chained attacks

**Chain 1 — Reset-mail flood as cover for the Ownership deletions (SEC-016 → SEC-001).**
Treated separately, one is spam and the other is data loss. Together they are an incident with the
alarm disabled. SEC-016 lets an attacker flood a target pilot's inbox from any web page with no Floaty
account; the pilot's mail from Floaty becomes noise they learn to ignore. The attacker then uses an
ordinary account and SEC-001 to delete that pilot's flights. Floaty sends no notification on flight
deletion, so the only signal was ever the pilot noticing — and their attention is already spent. The
flood also buries any genuine security mail Floaty might later send.

**Chain 2 — Read the track, then destroy the evidence (SEC-004 → SEC-001).**
SEC-004 hands an attacker the victim's full GPS history: home-area launch and landing coordinates,
with timestamps establishing when the pilot is reliably away from home. SEC-001 then deletes those
flights. The value is not just the deletion — it is that the record of *which* tracks were harvested
disappears with them, and with no soft-delete or audit trail the victim cannot tell what was read
before it was removed.

**Chain 3 — Overwrite plus re-point to launder ownership (SEC-002 → SEC-003).**
SEC-002 lets an attacker re-point a victim's flight at the attacker's own Spots and Glider, and
rewrite its description. SEC-003 lets them confirm the result. A victim's flight can thus be quietly
converted into something that reads as the attacker's, while still belonging to the victim's
account — corrupting the logbook in a way that is hard to notice and, without an audit trail,
impossible to attribute.

**Chain 4 — Enumerate every id, then take every track (SEC-024 → SEC-004).**
The report initially scoped SEC-004 as "another pilot's" track, which understates it. SEC-024 gives a
free existence oracle over the entire flight id space: 200 means the id exists, 500 means it does not.
An attacker sweeps the id range to build a complete inventory, then uses SEC-004 to pull the GPS track
for every one. The result is not one pilot's location history but the **whole corpus** — every launch
and landing coordinate Floaty holds, harvested by a single ordinary account.

**Chain 5 — Public hash, offline cracking, no brake (SEC-011 → SEC-023).**
The seeded `Floater` account's bcrypt hash sits in `data.sql` in a **public** repository. Pass 1 was
right to refuse to call that a disclosed credential — bcrypt is doing its job. But the three
conditions together are what matter: the hash can be attacked **offline** with no rate limit and no
detection; `spring.sql.init.mode=always` means the account is recreated on every boot even if someone
deletes it; and `email_verified=TRUE` means it bypasses the verification gate. SEC-023 then means
nothing on the live endpoint slows the login once a candidate is found. This is the chain that would
return SEC-011 to High, and it is the argument the original draft never assembled.

**Chain 6 — Heap exhaustion using someone else's upload (SEC-010 → SEC-004).**
SEC-010 notes that IGC uploads are unbounded, framed as *storage* exhaustion. The sharper vector is
*heap*: `FlightTrack.java:37` materialises the whole blob with `new String(igcData.getFile(), UTF_8)`,
so a `/track` request holds the raw bytes and a full character copy in memory at once, on a pod capped
at 2G (`docker-compose.yml:22-23`). Because SEC-004 removes the Ownership check, an attacker does not
need to own the large upload — they upload one oversized track once, then hammer `/track` against
**their own** flight id, or anyone's, to repeat the allocation at will.

**Trust boundaries nobody named.** Four, of which the report originally named only the first.

1. **A path variable is not an authorization decision.** All four Ownership findings share one
   unstated assumption: that `flightId` is *trusted input* because the request is authenticated.
   Authentication establishes **who is asking**; it says nothing about **what they may ask for**.
   Every by-id endpoint is a trust boundary crossing, and the Flight endpoints are where no check sits
   on it. `GliderController` and `SpotController` treat the same boundary correctly, which is why the
   fix is a pattern to copy rather than a design to invent.
2. **A local port number is being used as a credential.** `ManagementSecurityConfig.java:19-24`
   decides authorization by `request.getLocalPort() == 8081`, and grants `permitAll` to the *entire*
   chain when it matches — at `@Order(1)`, ahead of every application rule. The port is a property of
   the socket, not an identity: anything that reaches that port is trusted unconditionally. Today the
   blast radius is bounded by `management.endpoints.web.exposure.include`, but the boundary is
   enforced by a number, not by authentication.
3. **Untrusted bytes cross into unbounded heap allocation.** The IGC upload path goes from an
   attacker-controlled request body straight to a full-buffer `new String(...)` and a `@Lob` write,
   with `file_size` taken from the attacker-supplied array itself
   (`FlightApplicationService.java:36`) rather than measured independently. Nothing between the socket
   and the heap imposes a ceiling.
4. **`main` is a deployment trigger.** `argocd/apps/floaty-backend.yaml` syncs from `main` with
   `selfHeal: true` and `prune: true`, so a merge is a production deploy with no approval gate in
   between. That makes branch protection on `main` a production access control, not a code-review
   preference.

## Appendix C: the exploit tests

`src/test/java/ch/floaty/SecurityAuditTest.java` holds one `@Disabled` test per demonstrable finding.
All multi-pilot scaffolding lives in that one file rather than being spread across new per-controller
suites: an `owner` pilot who holds the records, and an `attacker` pilot who is **fully authenticated**
and owns nothing. Authentication is never the thing under test — that is the point.

| Test | Finding | Asserts once fixed |
|---|---|---|
| `deleteFlight_byNonOwner_isRejected` | SEC-001 | 403, and `deleteFlight` is never called |
| `updateFlight_byNonOwner_isRejected` | SEC-002 | 403, and `updateFlight` is never called |
| `readFlight_byNonOwner_isRejected` | SEC-003 | 403, and the owner's data is absent from the body |
| `readIgcData_byNonOwner_isRejected` | SEC-004 | 403 |
| `readFlightTrack_byNonOwner_isRejected` | SEC-004 | 403 |
| `readFlight_withUnknownId_isNotFound` | SEC-024 | 404 rather than 500 |
| `initiatePasswordReset_withTextPlain_isRejected` | SEC-016 | 415 for a `text/plain` body |
| `register_withTakenEmail_doesNotDiscloseExistence` | SEC-020 | the response does not disclose that the address is taken |

Every test is `@Disabled` on purpose, and each states in a comment the behaviour expected **once
fixed**. None asserts the defective behaviour as if it were intended — a passing test asserting that
any pilot may delete any flight would encode the bug as a specification. A fix ticket removes the
annotation and gets a red test to work against.

**Suite state: green — 36 tests, 0 failures, 9 skipped** (the 8 `@Disabled` tests above plus one
pre-existing `@Disabled` in `AuthenticationControllerTest`). The 27 previously passing tests are
unaffected. Run under JDK 17 with the system Maven, since `./mvnw` is broken in a fresh checkout
(#35).

**Why 8 tests for 25 Findings.** The ticket asks for one `@Disabled` test per *demonstrable* finding,
and these 8 are the demonstrable set — those provable through the HTTP surface with MockMvc. The
remaining 18 are not defects a single HTTP request can exhibit: they are configuration and deployment
facts (SEC-005, 011, 017, 018, 019, 022), properties of the dependency tree (SEC-012), design
observations recorded as non-defects (SEC-007, 013, 014, 015), or behaviours whose demonstration
would require wall-clock time, a second cluster, a stolen cookie or a multi-request sequence
(SEC-006, 008, 009, 021, 023, 025). SEC-010 is
demonstrable in principle but only by allocating a very large upload in the test suite, which would
trade a slow, memory-hungry test for a fact the code already makes plain.

**These were run once, enabled, to confirm they fail for the right reason** — a test that fails
because of a mock-setup error would be worthless to the fix ticket. Seven of the eight failed against
the real defect, and the observed behaviour is worth recording because it is the finding list restated
as evidence:

- `DELETE /flights/{id}` returned **204** — the other pilot's flight was genuinely deleted.
- `GET /flights/{id}/igc` returned **200** — the attacker received the owner's IGC file.
- `POST /auth/initiate-password-reset` with `text/plain` returned **200**.
- A nonexistent flight id returned **500**, not 404.
- The remaining ownership endpoints returned 500 from serialisation *after* fetching the victim's
  record — reached, not refused.

The eighth (`register_withTakenEmail_doesNotDiscloseExistence`) passes trivially against a mocked
service and is retained as a specification for the fix rather than as a demonstration.
